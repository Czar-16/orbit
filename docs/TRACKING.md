# Application tracking

Phase 7 is local and manual. Every imported job has one workspace-owned Application, with an append-only ApplicationEvent history. Preparation records Draft ready; preparation, links, notes, follow-ups and exports never submit anything. No authorized submission integration exists.

## Status and confirmation

Use Tracker to inspect an application. Mark as applied requires the checkbox confirming you submitted it yourself and an application date no later than today in Asia/Kolkata. It works without a draft. The date is stored at Kolkata midnight as a UTC timestamp; the actual confirmation time is stored separately. Both remain preserved through Interview, Offer, Rejected, Withdrawn and archive. Statuses report your input, not employer-verified information.

Only allowed transitions in PHASE-7-MODEL.md are accepted. Ready to apply additionally requires explicit review, a current active selected draft, an available private resume, current job/profile/preference versions, a nonempty letter, all displayed answers filled and no unresolved warnings. Do not invent answers to clear a warning; apply manually and record it afterwards if a question does not apply. Edit/regenerate resets readiness. Discard returns pre-application workflow to Needs review. After manual submission, further draft operations retain tracking status and the selected submission draft.

Tracking archive preserves its prior status and all dates/history; restore uses the recorded status. If a prior ready/draft state no longer passes the draft checks, restore safely uses Needs review, recording the original status and recheck outcome. It never fabricates readiness. Job visibility (saved/dismissed/archived) is separate: saving/unsaving and archive/restore synchronize pre-application workflow where appropriate, while dismissing/archiving a job never withdraws/rejects an application or changes an already confirmed application's progress.

All tracking commands use strict server-side Zod validation, expected application revision, and a transaction holding the workspace row lock. Follow-up changes also check the follow-up revision and application ownership. A stale tab is rejected; reload before retrying. SQL enforces ownership, selected-draft/job identity, confirmation consistency, positive revisions, mutually exclusive completion/cancellation and append-only event history. Migration baselines label observed legacy state at migration time, with no invented submission date or historical transitions.

## Notes, next steps and follow-ups

Notes append history and cannot be overwritten. A next step is bounded user-provided text; changes preserve the prior values in events. Follow-up labels and dates are user-provided. Due dates are Kolkata calendar dates stored at local midnight in UTC. Pending reminders may be edited, completed or cancelled; closed reminders cannot be silently reopened. Cancellation keeps history. No emails, scheduled notifications or external messages are sent. Scheduling belongs to Phase 8.

Tracker filters and pagination persist in the URL. Company/role/location refer to the latest supplied listing revision, with provenance badges. Source labels identify intake origins and do not establish employer verification. Applied date filters include confirmed later/archived states and use Kolkata day bounds. Filtering and sorting run in PostgreSQL before 20-row pagination, without the Discover view's 1,000-row cap.

Score filtering uses the Application's derived match projection: the selected draft's saved weighted score and version IDs, or the latest recorded WeightedMatch for the latest job revision when no draft is selected. Preparation pins this projection; discard falls back to recorded matches. Recording fresh matches updates only unselected applications. Unknown scores stay null and never satisfy a range, including minimum zero. The UI labels the projection source and compares job/profile/preference IDs to identify stale snapshots. Scores are inferred prioritization aids, never employer facts. Regenerate/select a current draft, or record matches from Discover, to update it.

Dashboard distinguishes real preparation events from unique active drafts, manually confirmed submissions (including later stages), current interviews/rejections, awaiting review, relevant intake today and pending overdue/upcoming reminders. Overdue means before today, upcoming means today through six days later. Queries use Asia/Kolkata; failed queries show Unavailable. Recent history includes actual import/draft/job/tracking events, explicitly labeled origins and migration baselines, and actual DiscoveryRun summaries. Latest ten tracking events and five discovery runs are shown; full event history is paginated in Tracker.

## Export

Settings offers one complete JSON snapshot and CSV files for each persisted entity. The repeatable-read snapshot includes workspace, profiles, private resume metadata, sources, jobs/revisions, skills/weighted matches, preferences, immutable drafts, applications/events/follow-ups, discovery runs and outbound request metadata. Environment values, credentials, original resume bytes and internal resume storage paths are not exported. Original bytes remain downloadable privately in Profile. Exports include private personal data and user-supplied answers: store them privately.

JSON retains IDs, UTC timestamps, provenance and nulls, with schema/timezone metadata. CSV includes all columns per entity, nested objects/arrays as JSON cells, quoted multiline/quote-containing text, null represented as the text `null`, and apostrophe-prefixed spreadsheet formula-leading cells (including whitespace/control prefixes). Use JSON when exact type/null distinction or original formula-leading text matters. Empty CSV tables contain no rows. Exports preserve saved empty unanswered draft fields; they never infer missing facts. This is data export, not backup restore or re-import.

Download routes accept only validated JSON/CSV/entity parameters, loopback Host, internal loopback URL with matching port, and Origin/Referer matching the actual Host (NextRequest normalizes loopback URL hostnames to localhost) and same-origin/user navigation fetch context. Responses are attachments with private no-store and nosniff headers. No database failure is reported as a successful export. [BACKUP.md](BACKUP.md) covers database plus private-resume backups. Export is complete and buffered in memory; very large workspaces may require the documented database backup instead.

## Validation and limits

Automated tests cover business rules, manual confirmation/date boundaries, UI commands/failures, real DB history/rollback/concurrency/readiness, pinned submission drafts, follow-ups, ownership, legacy backfill, filtering/counts and complete exports. No browser automation or listing-page requests occur. Manual visual/keyboard review at 320/768/1280 remains outstanding, as does SPA-history unsaved-edit handling. Normal navigation/unload guards use the existing hook. No new dependencies/services or AI calls were added.

Installed versions: Next.js 16.4.0, Prisma 7.10.0, Zod 4.6.6, React 19.3.0, PostgreSQL 18.6. Prisma client/types and migrate-diff CLI were inspected/generated locally. The current Prisma website redirects transaction documentation to ORM 8, so the installed 7.10.0 `$transaction`/transaction types are authoritative here; no ORM 8 API was adopted. Input and route behavior followed [Zod 4 API](https://zod.dev/api) and [Next Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers), plus installed typings. Migration uses PostgreSQL 18 `pg_input_is_valid` for safe historical summary parsing.

Saved profile/preferences changes and dismissal invalidate pre-application Ready to apply in the same workspace-locked transaction, appending an event while preserving the pinned evidence. Confirmed application history is unaffected.
